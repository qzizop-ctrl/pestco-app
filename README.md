# PEST — تطبيق متابعة زيارات العملاء

تطبيق لإدارة عملاء ومندوبي الشركة: تسجيل الزيارات، متابعة مراحل العميل (معاينة → عرض سعر → تركيب → صيانة)، تسجيل العروض وربطها بالموردين، وإدارة الموردين أنفسهم — مبني بـ React + Firebase، وشغّال على أندرويد (Capacitor) وويندوز (Electron) من نفس الكود.

## التقنيات المستخدمة
- **الواجهة**: React 18 + Vite + Tailwind CSS
- **الباك إند**: Firebase (Auth + Firestore)
- **تعدد المنصات**: Capacitor (أندرويد)، Electron (ويندوز)
- **تقارير/ملفات**: jsPDF وhtml2canvas (تصدير PDF)، xlsx (استيراد/تصدير إكسيل)
- **مراقبة الأعطال**: Sentry (اختياري)
- **الاختبارات**: Vitest

## التشغيل محليًا
1. `npm install`
2. انسخ `.env.example` إلى `.env` واملأ بيانات مشروع Firebase الخاص بيك (من Firebase Console → Project Settings → SDK setup). حقل `VITE_SENTRY_DSN` اختياري.
3. `npm run dev`

## قواعد أمان Firestore
المصدر الوحيد لقواعد الأمان هو `src/firestore.rules` (محدَّد في `firebase.json`) — لا توجد نسخة موازية له، تجنبًا لتعديل نسخة قديمة بالغلط وهي فعليًا مش المنشورة.

إعداد أول مرة على أي جهاز جديد:
```bash
npm install -g firebase-tools
firebase login
firebase use --add
```
وبعد أي تعديل في `src/firestore.rules`:
```bash
npm run firebase:deploy-rules
```
**تنبيه:** وجود القواعد في الكود لا يعني أنها مطبَّقة فعليًا على المشروع الحي — لازم تُنشر بالأمر أعلاه بعد كل تعديل.

### ما تفرضه القواعد الحالية
- **الإيميل لازم يكون مؤكَّد** (`email_verified`) لأي صلاحية: أدمن، عضو، أو مالك. التسجيل بإيميل/باسورد بيسمح لأي حد يسجّل بأي عنوان، فبدون الشرط ده كان ممكن حد يسجّل بإيميل زميل قبل ما الزميل نفسه يسجّل ويورث الصلاحية اللي اتدّت للعنوان ده.
- **المالك = أدمن فقط.** أي حساب غير مذكور في `config/admins` ما يقدرش يكتب في `users/{uid}/...` ولا ينشئ مستندات `access`، فالتسجيل المفتوح ما بقاش يقدر يملا Firestore ببيانات.
- **`access_by_email` بيكتبه الأدمن فقط** (كان أي مستخدم يقدر يكتب على أي إيميل).
- **الحذف النهائي للمالك/الأدمن فقط.** المحرر بيعمل حذف مبدئي (`deleted: true` + `last_change`) والمالك هو اللي يوافق.
- **`last_change.updatedById` لازم يساوي مستخدم الطلب** — مفيش تزوير نسبة تعديل لحد تاني.

### قبل النشر لأول مرة بعد التعديل ده
1. **تأكد إن حساب الأدمن الأساسي إيميله مؤكَّد.** سجّل دخول من النسخة الجديدة: لو مش مؤكَّد هيبعتلك رابط تأكيد ويطلعك برا، افتحه وارجع سجّل دخول. لو نشرت القواعد قبل كده ومفيش حد مؤكَّد هتتقفل بره.
2. الأعضاء (محررين/مشاهدين) اللي إيميلاتهم مش مؤكَّدة هيوصلهم رابط تأكيد أول ما يحاولوا يدخلوا.
3. `config/admins` (الأدمنز) قراءته للأدمن بس — أي مستخدم تاني طلبه بيترفض، والكلاينت بيتعامل مع الرفض ده كـ "مش أدمن" (`useAdminConfig.js`). مفيش حاجة إضافية مطلوبة.
4. **الأدمن مش بيفتح workspaces غيره.** الصلاحية على `users/{uid}/...` و`access/{uid}` و`auditLog` للمالك أو للعضو اللي المالك إدّاله دور بس؛ كون الحساب في `config/admins` لوحده ما بيديش قراءة ولا كتابة في workspace أدمن تاني (الموافقة والحذف النهائي والـ audit log للمالك بس). لو شغّال بأدمن واحد مفيش أي تغيير في سلوكك.

## حزمة xlsx وتثبيت سلامتها
حزمة `xlsx` بتتنزّل من رابط CDN مباشر (`cdn.sheetjs.com`) بدل npm registry — الأسلوب الرسمي من SheetJS. `package-lock.json` بيسجّل لها `integrity` (SHA-512 للـ tarball)، وبالتالي `npm install` و`npm ci` بيرفضوا أي ملف مش مطابق.

فوق ده فيه فحص إضافي اختياري على الملفات المثبَّتة فعليًا:
- `npm run xlsx:pin` يحسب SHA-256 للملفات المثبَّتة ويكتبها في `xlsx-integrity.json` (شغّلها مرة وأنت متصل بالإنترنت، ثم اعمل commit للملف).
- التحقق يحصل تلقائيًا بعد أي install (عبر `postinstall`). بدون الملف ده بيطلع تحذير بس، والـ lock يفضل هو خط الدفاع الأساسي.
- لو غيّرت نسخة `xlsx` في `package.json`، شغّل `npm run xlsx:pin` من جديد واعمل commit للملف المحدَّث.

## البناء والنشر
- **الويب (`dist/`)**: `npm run build` بيطلّع الواجهة اللي بيحملها أندرويد وويندوز. مفيش نسخة ويب/PWA بتتنشر.
- **أندرويد**: مجلد `android/` مرفوع في الريبو (اتولّد مرة واحدة). `npm run android:sync` ثم `npm run android:open` لفتحه في Android Studio.
- **ويندوز**: `npm run electron:build` → مجلد `release/`.

### النشر التلقائي (GitHub Actions)
- **أي push على `main`**: بيبني ويشغّل الـ lint والاختبارات ويحفظ الـ APK/المثبّت كـ artifact خاص (14 يوم). **مش بينشر Release.**
- **Release أندرويد**: `git tag android-v1.2.0 && git push origin android-v1.2.0` (أو Run workflow واكتب الإصدار).
  - **رقم الإصدار**: `versionName` = رقم الـ tag، و`versionCode` بيتحسب منه (`1.2.3` ← `1002003`، أي major×1,000,000 + minor×1,000 + patch) عشان أندرويد يقبل التحديث فوق النسخة القديمة. الـ minor/patch لازم يبقوا أقل من 1000 والـ major أقل من 2000. بناء من غير tag بياخد `versionCode` = رقم الـ run (صغير عن قصد، فمينفعش يتحسب نسخة رسمية).
  - **التوقيع**: النشر (tag أو إدخال إصدار) **بيفشل بوضوح** لو secrets الـ keystore مش مضافة (`ANDROID_RELEASE_KEYSTORE_B64` و`_PASSWORD` و`ANDROID_RELEASE_KEY_ALIAS` و`ANDROID_RELEASE_KEY_PASSWORD`). بناء عادي من غيرها بيطلّع APK **غير موقّع** (مينفعش يتثبّت) مع تحذير، والـ workflow بيفشل لو ماطلعش أي APK.
- **Release ويندوز**: `git tag win-v1.2.0 && git push origin win-v1.2.0`. رقم الإصدار بيتاخد من الـ tag ويتكتب في `package.json` وقت البناء، وelectron-builder بينشر Release `v1.2.0` ومعاه `latest.yml` اللي بيقراه الـ auto-updater. (قبل كده الإصدار كان ثابت 1.0.0 فالتحديث التلقائي عمره ما كان بيشوف نسخة أحدث.)
- **توقيع نسخة ويندوز** (اختياري، بيشيل تحذير SmartScreen): ضيف secrets `WIN_CSC_LINK` (ملف .pfx بصيغة base64) و`WIN_CSC_KEY_PASSWORD`.
- كل الـ workflows (الاختبارات، أندرويد، ويندوز، قواعد Firestore) بتستخدم `npm ci` عشان أي إصدار بيتبني بالظبط بالنسخ المثبّتة في `package-lock.json`. لو عدّلت `package.json`، شغّل `npm install` محليًا واعمل commit للـ lock، أو شغّل workflow «Sync package-lock.json» من تبويب Actions (من غير terminal) — `npm ci` هيفشل بوضوح لو الاتنين اتفرقوا.

## الاختبارات
```bash
npm test              # تشغيل مرة واحدة
npm run test:watch
npm run test:coverage # + تقرير تغطية في coverage/index.html
```
الاختبارات الحالية تغطي:
- **دوال بحتة (pure):** تواريخ اليوم بالتوقيت المحلي وتعديل الحقول اللي اتغيّرت بس وتخطي المكرر في الاستيراد (`helpers.recordSafety.test.js`)، صلاحيات الأدمن (`adminPermissions.test.js`)، حسابات لوحة التحكم (`dashboardCalculations*.test.js`)، استيراد الإكسيل (`helpers.excelImport.test.js`)، بناء العروض بما فيها سبب الرفض (`helpers.buildOffer.test.js`)، حماية الإكسيل (`excelSafety.test.js`)، منطق التذكيرات (`reminderLogic.test.js`)، كاش الـ snapshot (`snapshotCache.test.js`)، والتراجع عن آخر تعديل (`lastChange.test.js`).
- **Hooks بتكتب في Firestore** (Firestore متعمله mock، فبنتأكد من *إيه* بيتكتب و*إمتى* بيرفض): `useCustomerRecords.test.js` (إنشاء/تعديل/حذف مبدئي مع مهلة التراجع/تثبيت/مرحلة/تصفية موعد المكالمة، وإن الـ viewer والأوفلاين مبيكتبوش)، `useOfferActions.test.js` (العروض بـ transaction على آخر نسخة من السيرفر، وأسباب الرفض)، `useReminders.test.js` (التنبيهات داخل التطبيق).
- **تذكيرات أندرويد:** `notifications.test.js` (مزامنة الإشعارات المحلية مع قايمة العملاء).
- فلترة القوائم واكتشاف التكرارات (`hooks/useFilteredData.test.js`) ومكوّن كارت الملخص (`components/SummaryCard.test.jsx`) وغيرهم عبر `@testing-library/react`، وبيئة التشغيل `jsdom` (مُعدّة في `vite.config.js`). راجع [`CONTRIBUTING.md`](./CONTRIBUTING.md#إضافة-اختبارات) لو حابب تضيف اختبار مشابه.

`useAccessResolution` و`useWorkspace` ليهم اختبارات (حسم المالك/الدور، قرارات تسجيل الخروج، الكاش مقابل رد السيرفر، وتحويل الشاشات). لسه مفيش اختبارات end-to-end.

## التذكيرات
- **جوه التطبيق (كل المنصات):** بيفحص كل 15 ثانية ويطلّع صوت واحد + إشعار لكل تذكير حان ميعاده. كل جهاز بيفتكر التذكيرات اللي نبّه عليها بنفسه، فالـ viewer مبيتكررلوش التنبيه، والتذكيرات القديمة (فاتت بأكتر من نص ساعة، زي لما التطبيق يفضل مقفول كام يوم) بتتجمّع في إشعار واحد «مواعيد متابعة فاتت» وتفضل ظاهرة في التنبيهات.
- **أندرويد فقط — والتطبيق مقفول:** إشعارات محلية بتتزامن مع قايمة العملاء الحية، فموعد متابعة حد من الفريق بيوصل لكل الأجهزة اللي فاتحة الحساب (مش بس الجهاز اللي سجّله)، واللي اتمسح أو اتنفّذ بيتلغي. الحد الأقصى ~400 تذكير معلّق (حد أندرويد).
- **ويندوز:** مفيش تنبيه والتطبيق مقفول — ده محتاج push notifications من سيرفر (Cloud Functions + FCM)، وده مش متعمل.

## الأداء وحجم البيانات
كل العملاء والموردين بيتحمّلوا كاملين عند فتح التطبيق (مقصود — البحث والفلاتر والداشبورد والتذكيرات كلها محتاجة المجموعة كاملة). اللي اتعمل عشان ده يفضل مريح: أي مستند ما اتغيّرش بيفضل نفس الـ object بين الـ snapshots (`snapshotCache.js`)، فتعديل عميل واحد بيعيد رسم صفه هو بس مش القايمة كلها. وأول ما مجموعة توصل 2000 مستند بيتبعت تحذير لـ Sentry مرة في الجلسة. 

**تحسين الحسابات (بعد القياس):** كل snapshot بيعيد حساب القوايم المشتقة. اتقاس على بيانات تجريبية (كل عميل فيه 8 أنشطة و3 عروض): الفرز كان أكبر بند (~60ms عند 5000 عميل، ~270ms عند 20000) لأن المقارن كان بيحلّل التواريخ لكل مقارنة. دلوقتي مفاتيح الفرز بتتحسب مرة لكل سجل (`visitSort.js`)، وتاريخ آخر نشاط ومفاتيح الـ duplicates بتتخزّن لكل سجل في `WeakMap` (`customerDuplicates.js`) فالسجل اللي ما اتغيّرش ما بيتعاد حسابه. النتيجة: إعادة الحساب الكاملة نزلت تقريبًا من ~130ms إلى ~40ms عند 5000، ومن ~600ms إلى ~170ms عند 20000 (على Node — الموبايل أبطأ بعدة أضعاف). ده **مش بيقلل عدد المستندات المقروءة من Firestore**.

لو وصلتوا للرقم ده فعلًا وعايزين تقللوا القراءة نفسها، الحل الحقيقي (تقسيم «اللي بتعرضه القايمة» عن «اللي محتاجه الداشبورد» + عدّادات مجمّعة من Cloud Function) إعادة تصميم مش تعديل صغير — التفاصيل في تعليق `useLiveData.js`.
